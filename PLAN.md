# План реализации кнопок «О чем статья?», «Тезисы», «Пост для Telegram»

Основание: [PROJECT.md](./PROJECT.md).

## Текущее состояние

| Компонент | Статус |
|-----------|--------|
| Поле ввода URL | Готово |
| Парсинг статьи (`/api/parse`, `lib/parseArticle.ts`) | Готово |
| Интеграция с AI (`lib/openrouter.ts`) | Готово |
| Кнопка «Перевод» (`/api/translate`) | Готово — образец для остальных |
| Кнопки «О чем статья?», «Тезисы», «Пост для Telegram» | UI есть, после парсинга показывают сырой JSON вместо ответа AI |

Общий поток по PROJECT.md: **URL → парсинг → выбор кнопки → запрос к AI → вывод результата**.

---

## Порядок действий

### Шаг 1. Вынести общую подготовку текста статьи

Сейчас логика сборки `title + content` с обрезкой по длине дублируется в `app/api/translate/route.ts`.

1. Создать `lib/articleText.ts` с функцией `buildArticleText(title, content, maxLength?)`, которая формирует строку для промпта.
2. Подключить её в `/api/translate` вместо локального кода.

Это упростит три новых API-роута и сохранит единый лимит на размер текста.

---

### Шаг 2. API «О чем статья?» — краткое описание

1. Создать `app/api/summary/route.ts` по образцу `translate/route.ts`:
   - вход: `{ title, content }`;
   - валидация: хотя бы заголовок или контент;
   - вызов `chatCompletion` с системным промптом: краткое описание статьи на русском (2–4 предложения, без воды и комментариев);
   - ответ: `{ summary: string }` или `{ error: string }`.
2. Проверить вручную через `fetch` или UI после шага 5.

---

### Шаг 3. API «Тезисы» — ключевые мысли

1. Создать `app/api/theses/route.ts`:
   - тот же вход и валидация;
   - системный промпт: список основных тезисов на русском (маркированный список, 5–10 пунктов, только суть статьи);
   - ответ: `{ theses: string }`.
2. Проверить на той же тестовой статье.

---

### Шаг 4. API «Пост для Telegram» — готовый пост

1. Создать `app/api/telegram/route.ts`:
   - тот же вход и валидация;
   - системный промпт: пост для Telegram на русском (цепляющий заголовок, краткое изложение, 1–2 ключевых вывода, уместные эмодзи, до ~1500 символов, без хештегов и ссылок, если не указано иное);
   - ответ: `{ post: string }`.
2. Проверить длину и читаемость результата.

---

### Шаг 5. Подключить кнопки на фронтенде

Файл: `app/components/ReferentApp.tsx`.

1. После успешного парсинга для `summary`, `theses`, `telegram` вызывать соответствующий API вместо `JSON.stringify(article)`:
   - `summary` → `POST /api/summary`
   - `theses` → `POST /api/theses`
   - `telegram` → `POST /api/telegram`
2. Передавать в тело `{ title: article.title, content: article.content }` — как у перевода.
3. Обрабатывать ошибки по тому же шаблону, что и для `/api/translate`.
4. Обновить `LOADING_MESSAGES` для этих действий:
   - после парсинга — «Генерация ответа...» (или отдельные тексты для каждой кнопки).
5. Убедиться, что блок «Результат» показывает текст от AI, а не JSON.

---

### Шаг 6. Согласовать UI с PROJECT.md (при необходимости)

В PROJECT.md указаны **3 кнопки**, в приложении сейчас **4** (включая «Перевод»).

- Если оставляем «Перевод» — ничего не менять.
- Если нужна строгая трёхкнопочная версия — убрать действие `translate` из `ACTIONS` и связанный код в `handleAction`.

---

### Шаг 7. Проверка и доводка

1. Убедиться, что в `.env.local` задан `OPENROUTER_API_KEY`.
2. Прогнать сценарии:
   - пустой URL → сообщение об ошибке;
   - некорректный URL → сообщение об ошибке;
   - рабочая англоязычная статья → все три кнопки возвращают осмысленный русский текст;
   - недоступный сайт / пустой контент → понятные ошибки.
3. Запустить `npm run lint` и `npm run build`.
4. При необходимости подправить промпты по качеству ответов (длина, стиль, формат списка).

## Критерии готовности

- По нажатию каждой из трёх кнопок пользователь видит сгенерированный AI-ответ на русском, а не сырой JSON статьи.
- Ошибки парсинга, сети и OpenRouter отображаются в интерфейсе.
- Реализация следует паттерну существующего `/api/translate` без лишних абстракций.
